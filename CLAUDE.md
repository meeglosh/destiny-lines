# CLAUDE.md — Destiny Lines

Native iOS palm-reading app. User photographs their palm, a server-side pipeline gets it analyzed by OpenAI vision, and the app returns a structured reading. Free tier gives one simplified reading; subscribers get unlimited in-depth readings. Readings can be shared as a branded image.

---

## 1. Non-negotiable rules

Read these before writing any code. Violating them is worse than shipping slowly.

1. **No secrets in the app binary.** The OpenAI API key, the R2 access keys, and the Supabase `service_role` key must never appear in Swift source, `Info.plist`, `.xcconfig`, or the asset catalog. They live only in Supabase Edge Function secrets. The app ships only the Supabase project URL and the `anon` public key, which are safe by design because Row Level Security enforces access.
2. **The app never talks to OpenAI or R2 directly.** All of it goes through Supabase Edge Functions.
3. **Never commit** `.env`, `*.p8`, `*.p12`, `*.mobileprovision`, or `GoogleService-Info.plist`-style credential files. Check `.gitignore` before your first commit.
4. **The palm photo is never stored.** Delete the R2 object in a `finally` block on every exit path. Never log the image URL. Never write it to the device photo library or app storage. The app tells users this in its own UI, so it must be literally true. See §6.1.
5. **Nothing that is not a palm reaches the reading model.** Three gates, all mandatory: on-device hand detection, server-side safety moderation, and a cheap palm classifier. See §6.2. A rejection must never consume the user's free reading.
6. **Palm reading is entertainment.** Never generate or display content framed as medical, psychological, financial, or legal advice, and never predict death, illness, or lifespan. This constraint belongs in the OpenAI system prompt AND in a client-side guard. There is a disclaimer requirement in §9.
7. **Do not edit `DestinyLines.xcodeproj/project.pbxproj` by hand.** The project is generated by XcodeGen. To add a file, create the `.swift` file in the right directory and run `xcodegen generate`. If XcodeGen is not set up yet, that is task zero.
8. **Verify before claiming done.** A task is complete when `xcodebuild ... build` exits 0 and you have run the app in the simulator and taken a screenshot. Do not report success off a clean compile alone.
9. **Ask before adding a dependency.** The approved list is in §4. Nothing else without checking in.

## 6. The reading pipeline

This is the core flow. Build it end to end before polishing UI. Note that there are **three gates** before any expensive call happens, described in §6.2.

```
iOS app                    Edge Function          R2         Moderation      OpenAI
   |                            |                  |              |             |
[GATE 1: on-device hand detection — non-hands never leave the phone]
   |                            |                  |              |             |
   |-- POST /request-upload --->|                  |              |             |
   |                            |-- presign PUT -->|              |             |
   |<-- { uploadURL, key } -----|                  |              |             |
   |-- PUT jpeg (direct) ---------------------->   |              |             |
   |                                               |              |             |
   |-- POST /analyze-palm ----->|                  |              |             |
   |                            |-- presign GET -->|              |             |
   |                            |                                 |             |
   |            [GATE 2: omni-moderation — free, catches NSFW/illegal]          |
   |                            |-- image URL ------------------->|             |
   |                            |<-- flagged? --------------------|             |
   |                            |                                               |
   |            [GATE 3: cheap hand classifier on gpt-5.4-nano, detail:low]     |
   |                            |-- image URL, low detail ------------------->  |
   |                            |<-- { is_palm, reason } --------------------   |
```

### 6.1 Ephemeral image handling (this is a shipped feature, not just an implementation detail)

**The palm photo is never stored.** It exists in R2 only for the seconds between upload and analysis, and is deleted immediately afterward. This is a product promise the app makes to users in its own UI, so the implementation must be airtight enough that the promise is literally true.

Requirements, all mandatory:

1. **Delete in a `finally` block.** The R2 object must be deleted on every exit path from `analyze-palm`: success, moderation rejection, non-hand rejection, OpenAI timeout, JSON parse failure, unhandled exception. A `finally` is the only structure that guarantees this. Do not put the delete only on the success path.
2. **Backstop lifecycle rule** on the bucket: expire all objects under `palms/` after 1 hour. This catches the case where the function is killed mid-execution and never reaches its `finally`. The lifecycle rule is a safety net, not the mechanism.
3. **Presigned URLs expire in 5 minutes**, both PUT and GET. A leaked URL is useless almost immediately.
4. **Never persist the image or its URL anywhere else.** Not in the `readings` row, not in logs, not in error messages, not in `usage_events`. If Claude Code writes `console.log(imageUrl)` anywhere, that is a bug. Log the object key at most, and prefer logging nothing.
5. **Never save to the device photo library** and never write it to app container storage. Hold it in memory, upload, release.
6. **Strip all EXIF before upload**, including GPS coordinates, device identifiers, and timestamps. Re-encode the JPEG rather than trying to remove tags selectively.
7. **OpenAI retention: ZDR is NOT available on this account.** This is settled, not an open question. ZDR is not a self-serve toggle; it requires approval and is offered to eligible enterprise customers. This project runs on standard API terms, which means OpenAI generates abuse-monitoring logs for API usage and retains them for up to 30 days, unless longer retention is legally required. API inputs and outputs are not used for model training by default.

   **This constrains what the app is allowed to say.** The claim "we never store your photo" is true of Destiny Lines' own infrastructure and false as a claim about the whole pipeline. Copy must scope the promise to us and disclose the processor. Verify the current terms at developers.openai.com/api/docs/guides/your-data before the privacy policy is finalized, since retention terms change.
8. **Verify it.** Write an integration test that runs a reading, then asserts the R2 object returns 404. Also write one that forces a mid-pipeline failure and asserts the same. This is the test that keeps the marketing claim honest.

**User-facing copy.** Surface this prominently; it is a genuine differentiator and it reduces the friction of asking someone to photograph their hand.

Every line below is scoped to what we do, not to what the whole pipeline does. **Do not write copy that claims the photo is never stored anywhere.** See item 7 above.

- Capture screen (`DL-camera.png`), near the tip card: *"We delete your photo as soon as your reading is ready. We never keep it."*
- Analyzing screen (`DL-analyzing-palm.png`), small text under the progress copy: *"We delete your photo as soon as this finishes."*
- Settings, as a dedicated row that opens a short explanation: *"Your Privacy — how we handle your photo."* That explanation screen is where the OpenAI processor disclosure lives in plain language: the photo is sent to OpenAI to be analyzed, OpenAI may keep it briefly for safety monitoring, and it is not used to train their models.
- Paywall and App Store description: the short version, *"We delete your photo as soon as your reading is ready."*
- Privacy policy: the full version, naming OpenAI and Cloudflare as sub-processors and stating the retention window.

**Banned phrasings**, because they overclaim: "your photo never leaves your device" (false, it is uploaded), "no one ever sees your photo" (unverifiable), "100% private", "we never store images of your hand" without the scoping "we".

**Apple privacy nutrition label.** Photos are collected transiently, so declare them. Category: Photos. Not linked to identity, not used for tracking. Do not tick "Data Not Collected" just because the retention is short; that is inaccurate and is the kind of thing that draws a review rejection.

### 6.2 Content moderation

People will upload things that are not hands. Some of it will be innocuous and some will be deliberately abusive. **Nothing that is not a palm should ever reach the reading model or produce a reading.** Three gates, cheapest first.

**Gate 1 — on-device hand detection.** Use the Vision framework's `VNDetectHumanHandPoseRequest` on the captured or selected image before any upload happens. If no hand is detected above a confidence threshold, reject locally and re-prompt.

This is the most valuable gate and should be built first. It is free, instant, requires no network round trip, and means the majority of non-hand images **never leave the device at all**, which is both a privacy win and a cost win. The confidence threshold is a **constant you choose offline**. See §6.2a. Too strict rejects legitimate palms in poor lighting, which is a worse failure than letting one through to Gate 2.

Note that `VNDetectHumanHandPoseRequest` detects hand *pose*, so it will pass a back-of-hand photo. Palm-versus-dorsum discrimination is Gate 3's job.

**Gate 2 — safety moderation, server-side.** Run the uploaded image through OpenAI's moderation endpoint (`omni-moderation-latest`) before anything else. This endpoint is free and catches sexual content, violence, and self-harm imagery. Run it on every upload without exception. This gate exists for legal and App Store Review reasons, not cost reasons, and it must not be skipped even when Gate 1 passed.

If flagged: delete the R2 object immediately, return HTTP 422 with a generic code, record a strike, and do **not** tell the user which category tripped. A specific rejection message is a probing oracle.

**Gate 3 — palm classifier.** A short `gpt-5.4-nano` call with `detail: "low"` and a tight structured-output schema:

```json
{ "is_palm": true, "confidence": 0.0, "reason": "no_hand" | "back_of_hand" | "too_dark" | "too_blurry" | "partial" | "ok" }
```

Cost is roughly **$0.0002 per call**, which is about 2% of a premium reading. It pays for itself the first time it prevents a full reading call on a photo of someone's cat.

Only if `is_palm` is true and confidence clears the threshold does the expensive reading call happen.

**Rejection behavior.**
- Delete the R2 object immediately on any rejection.
- **Do not decrement the free reading allowance**, and do not count the attempt against the fair-use ceiling. Charging someone their one free reading for a blurry photo is the fastest way to lose them.
- Return the `reason` to the client and map it to a specific, in-character retry message. `too_dark` should say something about the light, not something generic. This is a UX opportunity, not just an error path.
- Log to `moderation_events` with the reason and outcome. Never log the image.

**Abuse handling.** Track strikes on `profiles.moderation_strikes`. On a Gate 2 flag, increment. At 3 strikes within 24 hours, apply a temporary cooldown on `request-upload` and return 429. Do not permanently ban on an automated signal alone; the classifier will produce false positives.

### 6.2a Choosing the Gate 1 and Gate 3 thresholds

**Nothing in this system self-calibrates.** The models analyze an image and return an answer. They do not retrain, and they do not adjust your thresholds. The confidence cutoffs for Gate 1 and Gate 3 are hardcoded constants, and the only defensible way to set them is an offline evaluation. Claude Code must not ship guessed values with a comment saying they will be tuned later.

Procedure, to be run once before launch and re-run whenever the model or the prompt changes:

1. **Collect a labeled set.** Target 200+ images, roughly half true palms and half negatives. Label each one by hand: `palm` / `not_palm`, plus the expected `reason` for negatives.
2. **Make it representative.** Real lighting (dim rooms, hard sun, mixed indoor color temperature), real skin tones across the full range, angles and rotations, motion blur, partial hands, busy backgrounds, gloved and jewelry-laden hands, and the specific negatives you expect: backs of hands, faces, pets, feet, screens, random objects.
3. **Run both gates over the set** and record the raw confidence for each image rather than a pass/fail verdict. Store the results as a CSV in the repo.
4. **Sweep the threshold** and compute precision and recall at each cutoff for both gates.
5. **Choose from the tradeoff, and state the objective explicitly.** For Gate 1 the cost of a false negative (rejecting a real palm) is a user who gives up, and the cost of a false positive is $0.0002 at Gate 3. **Those are not symmetric, so bias Gate 1 toward permissiveness.** Gate 3 should be the strict one, since a false positive there means a nonsense reading, which is the failure that generates refunds and one-star reviews.
6. **Commit the chosen values with the evidence.** The constants file should carry a comment giving the date, the model version, the dataset size, and the measured precision and recall at the chosen cutoff. A threshold without that provenance is a guess.

Skin tone coverage in step 2 is not a nicety. A hand detector that underperforms on darker skin will silently reject those users at a higher rate, and without a labeled set stratified by skin tone you will not find out.

Gate 2 has no threshold to set. The moderation endpoint returns its own verdict.

### 6.3 Client responsibilities

- **Downscale to a long edge of 1024px and JPEG-encode at ~0.8 quality before upload.** This is not optional and it is not merely a bandwidth optimization. See §7.1: on GPT-5.6 models with default `auto` detail, images are **not resized server-side**, so a full-resolution iPhone photo would be billed at roughly 12,000 image tokens instead of 768.
- Strip EXIF, including GPS.
- Run Gate 1 before uploading anything.
- Show the analyzing screen with a 60s timeout and a retry path.
- Never persist the photo. See §6.1.

### 6.4 `request-upload` function

- Requires a valid Supabase JWT. Reject unauthenticated requests.
- Rate limit: max 5 upload URLs per user per hour, and enforce the moderation cooldown here. Return HTTP 429 with a friendly in-character message.
- Object key format: `palms/{user_id}/{uuid}.jpg`. Presigned PUT expires in 5 minutes.

### 6.5 `analyze-palm` function

- Verify the JWT, and verify the `objectKey` prefix matches the caller's `user_id`. A user must not be able to analyze another user's object.
- Check entitlement server-side **before** spending anything on moderation or classification. This is the real enforcement point; the paywall UI is only a convenience. If the user is not subscribed and `free_readings_used >= 1`, return HTTP 402 with a code the app maps to "show paywall."
- Run Gates 2 and 3 in order. Abort on either.
- Presign a GET valid for 5 minutes and pass that URL to OpenAI. Set `detail: "high"` explicitly rather than relying on `auto`.
- **Delete the R2 object in a `finally` block.** See §6.1.
- Store only the resulting JSON in Postgres, plus a `usage_events` row with actual token counts from the API response.
- Use structured output (JSON schema) so the response parses deterministically. Do not regex-parse prose.
- Increment `free_readings_used` **only on a successful reading**, never on a rejection or error.

Tier differences, enforced in the system prompt, not the client:
- **Free:** `summary` ~60 words, each line `body` ~40 words, `traits` omitted, `timeline` contains only `near_future`, `key_insights` limited to 2.
- **Premium:** `summary` ~150 words, each line `body` 120 to 180 words with 3 to 5 traits, all three timeline entries at ~100 words each, 4 key insights.

### OpenAI system prompt requirements
- Frame as entertainment. State that readings are for amusement.
- Read the actual visible hand: line depth, length, breaks, forks, chains, mounts, finger proportion. Reference specific observed features so readings feel earned rather than generic.
- Warm, evocative, second person. Match the vintage-carnival-fortune-teller voice of the designs.
- Never mention death, lifespan, illness, diagnosis, pregnancy, financial outcomes, or legal matters.
- If the image is not a human palm, return a refusal marker so the app can show "we could not find a palm, try again."

## 7. Monetization and unit economics

### 7.1 Cost model

All figures computed from OpenAI's official published rates and the official image tokenization formula (developers.openai.com/api/docs/pricing and .../guides/images-vision, retrieved 25 July 2026). **Re-verify both before launch.**

**Yes, the image is counted.** Image inputs are metered and billed as input tokens. The earlier draft of this document used a rough 1,100-token estimate; that was wrong, and the correct figure is model-dependent. Here is the actual rule.

**Patch-based tokenization.** Models cover the image with 32x32px patches:

```
patch_count = ceil(width/32) x ceil(height/32)
image_tokens = patch_count x model_multiplier
```

Published multipliers: `gpt-5.4-mini` **1.62**, `gpt-5.4-nano` **2.46**, `o4-mini` 1.72. The GPT-5.4 flagship and the GPT-5.6 family have no multiplier, so patches map 1:1 to tokens. Note that the mini and nano multipliers mean **the cheap models are relatively more expensive on images than on text**, which partly offsets their headline discount.

For a palm photo downscaled to **768 x 1024** (long edge 1024, 3:4 portrait):

```
patch_count = ceil(768/32) x ceil(1024/32) = 24 x 32 = 768 patches
```

| Model | Multiplier | Image tokens | + prompt & schema | Total input |
|---|---|---|---|---|
| `gpt-5.4-mini` | 1.62 | 1,244 | 1,200 | **2,444** |
| `gpt-5.4-nano` | 2.46 | 1,889 | 1,200 | **3,089** |
| `gpt-5.4`, GPT-5.6 family | 1.0 | 768 | 1,200 | **1,968** |

Output assumptions: free reading ~500 tokens, premium reading ~2,000 tokens. The premium figure is padded because reasoning tokens are billed as output even though they never appear in the response.

**Cost per reading, standard tier:**

| Model | Rate in/out per 1M | Free | Premium | Premium + Gate 3 |
|---|---|---|---|---|
| `gpt-5.4-nano` | $0.20 / $1.25 | $0.0012 | $0.0031 | $0.0033 |
| **`gpt-5.4-mini`** | **$0.75 / $4.50** | **$0.0041** | **$0.0108** | **$0.0110** |
| `gpt-5.6-luna` | $1.00 / $6.00 | $0.0050 | $0.0140 | $0.0142 |
| `gpt-5.4` / `gpt-5.6-terra` | $2.50 / $15.00 | $0.0124 | $0.0349 | $0.0351 |
| `gpt-5.5` / `gpt-5.6-sol` | $5.00 / $30.00 | $0.0248 | $0.0698 | $0.0700 |

Gate 3 is the `gpt-5.4-nano` palm classifier from §6.2: a `detail: "low"` image is a fixed 512x512, so 256 patches x 2.46 = 630 tokens, plus a ~200-token prompt and a ~50-token structured verdict. **About $0.0002 per call.** Gate 2 (`omni-moderation-latest`) is free.

The shape of the number matters more than the number: **output tokens are roughly 80% of the cost.** The image is real but it is not the driver. This is why the fair-use ceiling and the output token cap in §7.5 target output, and why prompt caching on the static prefix is a nice-to-have rather than a lever.

**Use `gpt-5.4-mini` as the default.** Bake it off against `gpt-5.6-luna` and `gpt-5.4` on 20 real palm photos before committing. Keep the model name as one constant in the Edge Function.

### 7.1a The resolution trap

**GPT-5.6 models with `detail` set to `auto`, `original`, or omitted do not resize the image.** They preserve input dimensions. A raw iPhone photo at 3024 x 4032 is:

```
ceil(3024/32) x ceil(4032/32) = 95 x 126 = 11,970 patches
```

That is **11,970 image tokens instead of 768**, roughly 16x, and it turns a $0.014 reading into a $0.026 one on `gpt-5.6-luna` with no quality benefit for reading palm lines.

Two mandatory mitigations, both of them:

1. **Downscale client-side to a 1024px long edge** before upload. See §6.3.
2. **Set `detail: "high"` explicitly** in the API call rather than relying on the default. Never omit the parameter.

On `gpt-5.4-mini` the damage is capped, because `high` enforces a 1,536-patch budget and resizes to fit, so a full-res photo bills at 1,536 x 1.62 = 2,488 tokens rather than unbounded. That cap is a safety net that the GPT-5.6 family does not give you. It is not a reason to skip the client-side downscale.

R2, Supabase, and bandwidth remain negligible. R2 charges no egress and the objects live for seconds.

### 7.2 Apple's cut

- **Small Business Program: 15%.** A new developer with no earnings history automatically qualifies, and eligibility runs to $1M in annual proceeds. Enrolling is a form in App Store Connect, and the reduced rate takes effect 15 days after the end of the fiscal month in which you are approved. **Enroll on day one.** Failing to do so doubles Apple's cut for no reason.
- **Without the program: 30% in year one, 15% from a given subscriber's second year onward** on auto-renewable subscriptions. That year-two drop is standard and independent of the Small Business Program.
- EU developers on Digital Markets Act alternative terms see different rates. Out of scope for v1 US launch.

Net proceeds at the design's prices:

| Product | Gross | Net @ 15% | Net @ 30% |
|---|---|---|---|
| Monthly $4.99 | $4.99 | $4.24 | $3.49 |
| Yearly $39.99 | $39.99 | $33.99 | $27.99 |

Note that a yearly subscriber nets **less per month** than a monthly subscriber. Yearly wins on retention and cash up front, not on monthly margin. This is normal and is not a reason to change the prices.

### 7.3 The headline finding

**At $4.99 per month with `gpt-5.4-mini`, one subscriber's net proceeds cover roughly 385 premium readings per month**, inclusive of the Gate 3 classifier. The yearly plan at 15% covers roughly 3,090 premium readings per year. Nobody generates 385 palm readings in a month.

The conclusion Claude Code should internalize: **OpenAI cost is not the binding constraint on this business at the chosen prices.** The prices in the comps clear the cost bar by two orders of magnitude on a mid-tier model. The things that actually determine whether this is profitable are conversion rate, retention, and customer acquisition cost, none of which live in the codebase.

Readings covered by one month of subscriber net proceeds, at 15%:

| Model | Monthly sub ($4.24) | Yearly sub ($2.83/mo) |
|---|---|---|
| `gpt-5.4-nano` | 1,285 | 858 |
| `gpt-5.4-mini` | 385 | 257 |
| `gpt-5.6-luna` | 299 | 199 |
| `gpt-5.4` / `gpt-5.6-terra` | 121 | 81 |
| `gpt-5.5` / `gpt-5.6-sol` | 61 | 40 |

The bottom row is the only one where a heavy user could plausibly cost more than they pay. **Do not ship on a flagship model.** If a quality bake-off says you need `gpt-5.4` or better, revisit pricing before you revisit the cap.

### 7.4 Free tier cost

One free reading per install, at $0.0043 on `gpt-5.4-mini` including the Gate 3 classifier. Ten thousand installs that never convert costs about **$43 total**. This is a marketing expense smaller than a single day of modest ad spend. Do not compromise the free reading's quality to save money; it is the entire conversion mechanism.

The 3-day free trial is similarly cheap. Even a trial abuser who runs 30 readings then cancels costs $0.33. Design against trial abuse for product-integrity reasons if you like, but not for cost reasons.

### 7.5 Revised guardrails

This supersedes the earlier 60-reading cap, which was set before the cost math was done and was far too tight.

- **Fair-use ceiling: 150 premium readings per user per month.** At `gpt-5.4-mini` this caps a single user's cost at $1.65 against $4.24 net, a 61% floor on gross margin in the absolute worst case. In practice almost nobody will approach it. Return HTTP 429 with a warm in-character message, not an error dump.
- **Free tier: exactly 1 reading, enforced server-side** against `profiles.free_readings_used`.
- **Log every call** to `usage_events`, including the Gate 3 classifier calls, using the actual token counts returned by the API rather than the estimates in §7.1. Compute `cost_usd` from a rate table constant in the function so historical rows stay accurate when prices change.
- **Rejections are not free reads.** A Gate 2 or Gate 3 rejection must not decrement `free_readings_used` or count against the ceiling. See §6.2.
- **Downscale client-side and set `detail: "high"` explicitly.** See §7.1a. This is the single largest input-side cost risk in the system.
- **Set a hard monthly spend limit on the OpenAI account itself.** This is the real backstop against a bug or an abuse campaign. Start at $200.
- **Enable prompt caching.** The system prompt and JSON schema are identical on every call and exceed the 1,024-token cache minimum. Cached input on the GPT-5.4 family is billed at 10% of standard input. This is a small saving in absolute terms but it is free to implement: keep the static prefix byte-identical and put the image last.
- **Do not use the Batch API.** The 50% discount requires up-to-24-hour turnaround. Users are staring at an analyzing screen.
- **Cap output length** with an explicit token limit so a runaway generation cannot bill unbounded output.

### 7.6 Pricing options

The design comps specify Option A. All three are viable and all three cover costs comfortably. Build the paywall so the products are data-driven, loaded from `Product.products(for:)` against IDs in a single constants file, so switching options later is a configuration change and an App Store Connect edit, not a redesign.

**Option A — as designed. Recommended for launch.**

| Product ID | Price | Net @ 15% |
|---|---|---|
| `com.destinylines.premium.monthly` | $4.99 / mo | $4.24 |
| `com.destinylines.premium.yearly` | $39.99 / yr, 3-day trial | $33.99 |

Yearly is 33% cheaper per month than monthly, which matches the "SAVE 33%" badge in `DL-paywall.png`. The copy is already correct; do not recompute it.

**Option B — add a one-time unlock.** Since COGS is trivial, the constraint is willingness to pay, and a meaningful share of users will never accept a subscription for a novelty app but will pay once out of curiosity.

| Product ID | Type | Price | Net @ 15% |
|---|---|---|---|
| `com.destinylines.reading.single` | Consumable | $2.99 | $2.54 |

Use a **consumable**, not a non-consumable, since it grants one in-depth reading rather than permanent access. Consumables are not restored by `AppStore.sync()`, so the grant must be recorded server-side in `profiles.reading_credits` at purchase-verification time or a user who reinstalls loses what they paid for. This is the main implementation cost of Option B and the reason it is not the launch default.

**Option C — higher price point.** If early conversion data shows price is not the objection, $7.99/mo and $49.99/yr are both standard App Store tiers and neither changes the cost picture at all. Worth an experiment once you have a baseline, not before.

### 7.7 Break-even sketch

Not a code requirement, but the number Claude Code should not accidentally undermine with an expensive default.

At `gpt-5.4-mini`, a monthly subscriber doing a realistic 8 readings per month costs $0.09 against $4.24 net. **Gross margin is roughly 98%.** The business fails or succeeds on install volume and conversion, not on inference spend. Every engineering decision that improves the free reading's quality, the analyzing screen's perceived magic, or the share card's shareability is worth more than any cost optimization in this document.

### 7.8 StoreKit implementation

- `StoreManager` as an `@Observable` type. Load with `Product.products(for:)`, purchase with `product.purchase()`, verify with `VerificationResult`. Never trust an `unverified` result.
- Run a `Transaction.updates` listener for the app's lifetime to catch renewals, refunds, and Ask-to-Buy approvals.
- Derive entitlement from `Transaction.currentEntitlements` on launch and on every foreground.
- **Restore Purchases** is required on the paywall. Call `AppStore.sync()`.
- Mirror entitlement to Supabase: POST the signed transaction JWS to `verify-subscription`, which validates it and updates `profiles.subscription_status`, `subscription_expires_at`, and `original_transaction_id`. Server-side entitlement is what `analyze-palm` enforces; the paywall UI is only a convenience.
- Add an App Store Server Notifications V2 webhook so cancellations, refunds, and billing failures propagate without the app opening.
- **Fail open toward the paying customer.** If the server cannot confirm entitlement but StoreKit says the user is subscribed, allow the reading and reconcile later.
- Until the Apple Developer Program enrollment completes, drive everything from a local `Products.storekit` configuration file so purchase flows are fully testable in the simulator. Switching to the real App Store must require zero code changes, only removing the scheme's StoreKit config override.

```sql

created_at   timestamptz default now()
gate         text not null   -- device | safety | classifier
outcome      text not null   -- passed | rejected
reason       text            -- no_hand | back_of_hand | too_dark | too_blurry | partial | flagged

model          text not null
tier           text not null
input_tokens   int  not null
cached_tokens  int  default 0 not null
output_tokens  int  not null
cost_usd       numeric(10,6) not null

-- readings
id          uuid primary key default gen_random_uuid()
user_id     uuid not null references profiles(id) on delete cascade
created_at  timestamptz default now()
tier        text not null              -- free | premium
content     jsonb not null             -- the reading JSON from §6
```

Enable RLS on both. Policy on each: `auth.uid() = id` / `auth.uid() = user_id` for select. Inserts and updates happen only via Edge Functions using the service role. The client must never be able to write `free_readings_used` or `subscription_status`.

Indexes: `readings (user_id, created_at desc)`, `usage_events (user_id, created_at desc)`, `moderation_events (user_id, created_at desc)`.

**No table stores an image, an image URL, or an object key beyond the life of the request.**

## 14. Open items for the owner

Do not guess on these. Surface them and wait.

- Apple Developer Program enrollment, needed before any device testing of purchases or App Store submission.
- **App Store Small Business Program enrollment**, immediately after the developer account exists. This halves Apple's commission from 30% to 15% and takes effect 15 days after the end of the fiscal month of approval, so enrolling late costs real money. See §7.2.
- A hard monthly spend limit configured on the OpenAI account. See §7.5.
- A model quality bake-off on ~20 real palm photos before locking in `gpt-5.4-mini`. See §7.1.
- A labeled evaluation set of 200+ real palm and non-palm photos, needed before Gate 1 and Gate 3 thresholds can be set. This is a data collection task for the owner, not something Claude Code can generate. See §6.2a.
- Legal review of the privacy policy's processor disclosure, since ZDR is not available and the photo does transit OpenAI. See §6.1 item 7.
- Privacy policy wording covering transient R2 storage and OpenAI transit, and the Apple privacy nutrition label declaration for Photos.
- Privacy policy and terms URLs, required by App Store Review for a subscription app.
- Font licensing for the display face.
- What the INSIGHTS tab in the history tab bar should contain.
- Whether users should be able to create a real account (email or Sign in with Apple) to carry readings across devices, or whether anonymous-only is acceptable for v1. Anonymous-only means a lost device means lost readings and a potentially lost subscription link.
